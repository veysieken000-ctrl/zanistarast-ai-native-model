# Zanistarast.com — Ease of Use and Public UX

Status: LOCKED — Roadmap item 21

## Principle

A visitor should understand what zanistarast.com offers and begin watching, reading, listening or exploring without needing academic knowledge, Zanistarast terminology, a tutorial or an account.

Depth remains available, but complexity is progressive: the first interaction is simple; source, provenance and deeper conceptual material are reachable when wanted.

## First-visit clarity

The initial public experience should quickly communicate:

- what can be watched/read/listened to;
- how to start a work;
- how to search or browse;
- how to discover by values/themes;
- how to continue into explanation and sources.

Internal workflow states, repository language and academic production terminology must not dominate public navigation.

## Core navigation

The primary navigation should remain small and stable. Candidate destinations include:

- Home;
- Discover;
- Search;
- Library/Saved when available.

Secondary areas such as About, Sources/Method, accessibility, legal/privacy and account settings belong in appropriate secondary navigation rather than competing with the main task.

Labels should use ordinary public language and be tested before adding more top-level destinations.

## Work cards

A public work card should communicate only what helps a visitor decide whether to open it, such as:

- title;
- meaningful image/poster where applicable;
- media/form indicator;
- concise context;
- duration/reading time where useful;
- audience/context indicator where important.

Cards should not be overloaded with internal review badges, technical IDs or dense provenance. Deeper information remains available on the work page.

## Work-page hierarchy

The page should follow the already locked journey:

SEE — primary representation;
FEEL — coherent human/narrative experience;
UNDERSTAND — concise explanation and expandable public reading;
DEEPEN — provenance, source and deeper material.

Important controls should appear where visitors expect them and remain consistent across works.

## Progressive disclosure

Complex information should be layered rather than removed:

1. immediate title/media/context;
2. short explanation;
3. expandable public-language reading;
4. source/provenance;
5. deeper scientific/conceptual record where applicable.

Simplification must not hide a material warning, uncertainty, audience restriction or source/adaptation distinction needed to avoid misunderstanding.

## Search and discovery

Search should tolerate ordinary-language queries rather than require exact canonical titles. Discovery should work through themes/values, formats, cultures/collections and language as defined in Item 11.

Empty results should offer understandable alternatives without inventing content.

## Account boundary

Core public viewing/reading should not require account creation. Authentication may be required for genuinely personal features such as synchronized likes, saved works or cross-device history.

The product should not interrupt first use with unnecessary registration pressure.

## Feedback and errors

User-facing failures should be clear and actionable without exposing raw backend/provider errors.

Examples:
- media temporarily unavailable;
- this version has been withdrawn or replaced;
- no translation is available yet;
- network connection lost;
- a feature requires sign-in.

The interface must never fabricate a successful playback, source, translation or saved action when the underlying operation failed.

## Accessibility as usability

Ease of use includes:
- keyboard navigation;
- visible focus;
- screen-reader semantics;
- captions/transcripts where applicable;
- readable typography;
- adequate touch targets;
- text alternatives;
- reduced-motion respect;
- no essential meaning conveyed by color alone.

Accessibility must be part of the base experience, not a separate “special” site.

## Language

Public UI text should be concise, natural and translatable. Internal English identifiers may remain in code/data, but user-facing language should follow the selected locale.

Specialist Zanistarast terms may appear when useful, with plain-language explanation rather than being prerequisites for navigation.

## Ethical interaction design

The product must not gain ease of use by manipulating attention. Avoid:
- deceptive buttons;
- disguised advertisements;
- false urgency;
- forced autoplay with sound;
- difficult cancellation/back navigation;
- unnecessary notification prompts;
- misleading thumbnails;
- dark patterns that push sign-up or continuous viewing.

## Performance perception

Primary content and controls should become usable before secondary recommendations or heavy decorative media where practical. Loading states should communicate real progress without pretending completion.

Low-bandwidth and mobile users should not be treated as secondary.

## Consistency

Shared actions such as Like, Save, Share, Read, Source, Back and Play should behave consistently across the product. A familiar action should not change meaning between pages.

New features should fit the existing hierarchy rather than adding a new navigation model each time.

## Item 21 acceptance criteria

1. First-time visitors can begin using the site without a tutorial.
2. Core navigation stays small and uses public language.
3. Work cards prioritize decision-useful information.
4. See → Feel → Understand → Deepen defines the work-page hierarchy.
5. Complexity is progressively disclosed, not simply removed.
6. Search accepts ordinary-language discovery.
7. Core public consumption does not require an account.
8. Errors are actionable and do not leak provider internals.
9. Failed operations are never represented as successful.
10. Accessibility is part of the default UX.
11. UI language is translatable and specialist terms are explained.
12. Dark patterns and manipulative attention design are excluded.
13. Primary content loads ahead of secondary heaviness where practical.
14. Common actions remain consistent throughout the product.
